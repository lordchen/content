# ContentWork V2 大版本产品与开发规划

## 1. 当前判断

当前原型已经证明了最小闭环：

- 抖音总热榜可以采集、入库、导出到页面。
- 固定对标账号池可以作为结构输入。
- 运营可以选择热点和对标结构，确认后调用 Codex CLI 生成脚本。
- 脚本可以写入 SQLite，并在页面展示分镜、口播、字幕和来源关系。

但它仍然只是 MVP，不是目标系统。核心差距有四类：

1. 产品形态仍像技术验证页，不像运营每天使用的工作台。
2. 数据输入过薄，主要是热榜标题和固定对标结构，缺少真实视频、字幕、商品活动和账号内容表现。
3. 脚本质量没有稳定控制，只是一次生成，没有评分、改写、人工反馈闭环。
4. 采集策略依赖平台页面和登录态，稳定性不够，需要多条替代数据链路。

V2 的目标不是继续微调单页原型，而是把系统重构为“每日内容生产工作台”。

## 2. 最终目标

ContentWork 的最终目标：

> 每天自动把平台热点、对标账号内容、品牌信息、商品活动和历史表现转化为可拍短视频脚本库，并让运营可以选择、审核、改写、回填效果。

系统最终要服务三个动作：

1. **找题**：今天哪些热点、对标内容、类目趋势值得做。
2. **成稿**：把选题变成可拍脚本，而不是泛泛文案。
3. **复盘**：记录哪些脚本被采用、发布后表现如何，再反向优化筛选和生成。

核心角色：

- 运营：每天选择素材、生成脚本、筛选可拍版本。
- 内容负责人：看每日推荐、审核风险、查看产出质量。
- 系统管理员：维护品牌、对标账号、采集源、平台登录态和数据质量。

## 2.1 大版本产品蓝图

V2 大版本不能只理解为“多做几个页面”，而是要把系统变成一个每天可重复使用的生产系统。

最终交付物：

- 每天生成 N 条候选脚本。
- 每条脚本都有分镜、口播、字幕、来源热点、对标结构、商品活动、质量分和风险提示。
- 每条脚本都能进入审核、采用、待改、弃用、发布回填和模板沉淀。
- 每天结束时，系统能留下“今天用了什么输入、产出了什么脚本、哪些被采用、哪些值得复用”的记录。

角色体验：

- 运营每天从“今日工作台”开始，只看今天要处理的采集保障、推荐选题、待审核脚本和发布回填。
- 内容负责人看“今日生产闭环”和“复盘洞察”，判断今天卡在哪一步、脚本质量是否够拍、哪些结构值得复用。
- 采集维护人员看“采集任务中心”，处理登录态、验证码、失败截图、人工导入和第三方表格兜底。
- 品牌负责人在“品牌商品中心”维护今天可说的商品活动、权益限制、禁用承诺和门店范围。

数据保障原则：

- A 层公开热榜是稳定主干。
- B 层登录态小批量只能作为增强，不能作为唯一入口。
- C 层人工导入必须是正式功能，不是临时补救。
- D 层第三方表格先做导入和清洗，深度 API 集成后置。

大版本拆包：

1. R1 生产闭环版：今日工作台、生成脚本、首页审核队列、脚本库复盘。
2. R2 输入增厚版：对标内容池、字幕任务、结构摘要、商品活动输入。
3. R3 质量引擎版：质量评分、风险校验、自动改写、模板复用。
4. R4 采集保障版：每日采集计划、登录态健康、失败兜底、第三方表格流程。

下一档成熟度缺口：

- 真实字幕服务：不能长期只靠手工字幕和结构摘要兜底，需要视频链接自动创建字幕任务。
- 对标账号内容更新：不能只维护账号元数据，需要定期导入近期视频/笔记、字幕、表现和结构。
- 质量反馈学习：不能只靠规则评分，需要把采用、待改、弃用和发布表现反向影响选题推荐和脚本改写。
- 第三方数据清洗：不能只支持粘贴表格，需要稳定字段识别、去重、平台标注、风险提示和批量处理。

## 3. V2 产品结构

V2 拆成 6 个页面，而不是继续塞在一个原型页里。

### 3.1 今日工作台

这是默认首页，用于每日运营。

必须展示：

- 今日数据状态：热榜采集是否成功、对标采集是否成功、字幕任务数量、脚本生成数量。
- 今日推荐选题：系统筛选出的 5-10 个候选。
- 待处理任务：缺字幕、缺商品信息、待确认、生成失败。
- 今日脚本产出：已生成、已采用、待审核。

关键体验：

- 首页不展示历史旧结果污染当前工作流。
- 每天进入时是一个新的工作日批次。
- 历史脚本进入“脚本库”，不默认出现在今日工作台。

### 3.2 热点池

用于看平台热点和品牌相关性。

字段：

- 平台：抖音、小红书、手工录入、第三方源。
- 标题/话题。
- 热度值或排名。
- 时间。
- 类目猜测。
- 品牌相关性评分。
- 可用方式：可直接借势、只借结构、只观察、不可用。
- 风险标签。

操作：

- 加入今日候选。
- 标记不相关。
- 标记风险。
- 手工补充解释。

当前原型已落地：

- 独立热点池页面。
- 读取真实抖音热榜入库数据。
- 展示品牌相关性、风险等级和使用状态。
- 支持加入今日候选、设为观察、标记不相关、屏蔽风险。
- 标记结果不覆盖原始热榜数据，写入运营判断表。

### 3.3 对标内容池

不是只存账号，而是存账号内容和结构。

对象：

- 对标账号。
- 对标视频/笔记。
- 标题、封面、链接、发布时间。
- 字幕文本。
- 结构摘要。
- 表现指标，如果能拿到则存点赞、评论、收藏、转发。

操作：

- 添加对标账号。
- 导入视频链接。
- 提取字幕。
- 生成结构摘要。
- 加入今日候选。

当前原型已落地：

- 独立对标内容池页面。
- 单条导入：标题、平台、链接、账号、字幕或备注。
- 批量导入：支持一行一条链接，也支持第三方表格粘贴。
- 内容列表：展示平台、账号、字幕状态、结构状态、是否已加入生成工作流。
- 批量动作：批量加入生成工作流、批量生成结构摘要。
- 全站左侧菜单已把“对标内容池”放在热点池和脚本流程之间，明确它是脚本生成前的素材处理环节。

### 3.4 品牌与商品中心

脚本质量必须依赖品牌和商品信息，不能只靠品牌名。

字段：

- 品牌基础信息。
- 目标人群。
- 门店/城市/平台。
- 商品 SKU 或商品组。
- 当前活动、价格、权益、使用条件。
- 禁用词、禁用承诺、合规边界。
- 推荐表达风格。

操作：

- 编辑品牌。
- 新增活动。
- 标记本周重点商品。
- 维护合规规则。

当前原型已落地：

- 独立品牌商品中心页面。
- 新增商品活动：商品/活动名、商品组、卖点、活动规则、价格/合规说明、门店范围。
- 当前商品活动列表：显示已加入生成状态、活动规则、合规说明和可说卖点。
- 可加入或移出生成输入；只有已加入的商品活动会被脚本生成读取。
- V2 首页保留快捷添加，但正式维护入口是品牌商品中心。

### 3.5 生成工作流

这是目前原型的重构版。

标准流程：

1. 选择热点或对标内容。
2. 选择品牌和商品活动。
3. 系统完成结构分析。
4. 设置生成数量和脚本类型。
5. 生成候选脚本。
6. 评分、改写、入库。

必须明确三种状态：

- 输入素材：热点、对标、商品。
- 中间分析：字幕结构、热点角度、品牌嫁接点、风险。
- 输出结果：可拍脚本。

当前原型已落地：

- 脚本流程页读取 `GET /api/v2/dashboard` 的 `generationReadiness`。
- 生成前检查展示已确认热点/对标、可读取人工结构、商品活动输入和高表现模板。
- 生成前证据链展示当前会读取的商品活动和已加入的结构素材，并提供跳转到品牌商品中心、对标内容池维护输入。
- 生成按钮会在关键输入缺失时提示缺项，避免只凭品牌名和热词生成低质量脚本。

### 3.6 脚本库与复盘

这是历史资产区。

字段：

- 生成日期。
- 来源热点。
- 来源对标。
- 使用商品/活动。
- 脚本内容。
- 质量评分。
- 采用状态。
- 发布链接。
- 发布表现。
- 复盘结论。

操作：

- 标记采用。
- 复制脚本。
- 回填发布数据。
- 标记优质模板。
- 作为后续生成参考。

## 4. 数据采集替代方案

V2 不把成功押在单一采集方式上。平台采集分成 A/B/C/D 四层。

### A 层：稳定自动源

优先保留当前已跑通的抖音总热榜。

适合：

- 每天稳定拿到热点词。
- 做早期候选池。
- 不依赖复杂搜索页。

当前已有：

- `scripts/fetch_douyin_hot_search.py`
- `hot_search_runs`
- `hot_search_items`
- `brand_hot_candidates`

V2 要补：

- 小红书热榜或第三方热点源。
- 热榜采集状态页。
- 失败告警和最近成功时间。

### B 层：登录态浏览器采集

用于类目词搜索和对标账号页面。

适合：

- 抖音搜索词结果。
- 小红书搜索词结果。
- 对标账号主页。

原则：

- 只做小批量。
- 每次 3 个词以内。
- 需要人工登录态。
- 遇到验证码明确暂停，不做伪自动化。

当前已有：

- `scripts/douyin_login_init.js`
- `scripts/douyin_category_capture.js`

V2 要补：

- 采集任务队列。
- 登录态健康检查。
- 失败截图和 HTML 留存。
- 结构化结果解析。

### C 层：人工导入源

这是必须保留的替代方案，不能只依赖自动抓取。

适合：

- 运营在抖音/小红书看到好视频后复制链接。
- 对标账号池固定维护。
- 平台风控导致自动采集不可用时继续工作。

输入方式：

- 单条链接导入。
- 批量链接导入。
- 飞书表格导入。
- 手工粘贴字幕或标题。

V2 必须把人工导入做成正式功能，而不是临时兜底。

### D 层：第三方数据源

作为后续增强，不作为 V2 首发依赖。

候选：

- 灰豚、蝉妈妈、飞瓜、新榜等平台。
- 品牌已有 BI 或投放数据。
- 手工导出的 Excel/CSV。

原则：

- 先支持 CSV/表格导入。
- 不急着做深度 API 集成。
- 所有第三方数据必须标注来源和时间。

### 4.1 数据源状态机

采集中心不能只展示“某个任务成功或失败”，而要判断今天每个数据源是否能支撑生产。

V2 将数据源拆成状态矩阵：

- A 层公开热榜：稳定自动源，只代表热点词和热度排序。
- B 层登录态小批量：增强来源，依赖登录态，验证码或登录失效时必须暂停。
- C 层人工导入内容池：正式兜底来源，导入后必须补字幕或结构摘要。
- D 层第三方表格：批量兜底来源，必须预检字段、去重、标注平台和风险。
- E 层字幕和结构摘要：决定脚本质量的结构输入。
- F 层脚本库复盘：把采用、待改、弃用、发布表现和模板反哺下一轮生成。

状态机每个来源必须说明：

- 当前状态：已就绪、可使用、需兜底、待处理。
- 当前证据：最近成功时间、数量、失败原因或导入数量。
- 能产出什么：热点、链接、字幕、结构、模板或反馈信号。
- 风险边界：不能把热榜当字幕，不能强行绕过验证码，不能把占位任务当真实采集。
- 下一步动作：运行采集、人工导入、第三方表格预检、补字幕结构化或回填复盘。

## 5. 脚本质量提升链路

V2 的脚本生成不能只做一次 prompt。

标准链路：

`素材 -> 字幕/结构摘要 -> 品牌商品匹配 -> 初稿生成 -> 质量评分 -> 二次改写 -> 入库`

### 5.1 字幕结构摘要

输入：

- 对标视频链接。
- 手工字幕。
- 旧项目 `video-tools` 字幕接口。

输出：

- 前 3 秒钩子。
- 情绪点。
- 冲突点。
- 镜头节奏。
- 转场方式。
- CTA。
- 可借鉴结构。
- 不可复用风险。

### 5.2 商品活动匹配

脚本必须知道今天推什么。

输入：

- 商品组。
- 活动权益。
- 价格或折扣。
- 门店范围。
- 使用限制。

输出：

- 适合接哪个热点。
- 适合借哪个对标结构。
- 哪些表达不能说。

### 5.3 生成提示词升级

每条脚本必须输出：

- 标题。
- 前 3 秒开头。
- 15 秒分镜。
- 每段镜头动作。
- 出镜人。
- 场景。
- 道具。
- 口播。
- 屏幕字幕。
- 剪辑提示。
- CTA。
- 风险提示。
- 来源依据。

禁止输出：

- 纯方向建议。
- 没有具体镜头的文案。
- 虚构优惠。
- 未授权明星/赛事/平台 logo 表达。

### 5.4 质量评分

每条脚本生成后打分：

- 可拍性。
- 开头吸引力。
- 品牌贴合度。
- 商品/活动承接度。
- 转化明确度。
- 合规风险。

低于阈值自动重写一次。

## 6. V2 技术架构

### 6.1 后端

建议从当前 Python HTTP 原型升级为 FastAPI。

模块：

- 数据采集服务。
- 素材导入服务。
- 字幕任务服务。
- 结构摘要服务。
- 脚本生成服务。
- 脚本库服务。
- 品牌商品服务。

短期仍可复用 SQLite；当任务和多人协作变多后迁移 PostgreSQL。

### 6.2 前端

建议从单页静态原型升级为多页面应用。

可以继续先用原生 HTML/CSS/JS 做 V2 原型，但结构要按页面拆：

- `dashboard`
- `trends`
- `benchmarks`
- `brand`
- `generator`
- `scripts`

如果继续扩大，建议迁移到 Next.js 或 React。

### 6.3 数据模型

V2 需要新增或重构这些核心表：

- `workdays`：每日批次。
- `trend_items`：多平台热点。
- `content_sources`：视频/笔记/链接统一素材表。
- `subtitle_jobs`：字幕任务。
- `content_structures`：结构摘要。
- `brand_products`：商品和活动。
- `generation_jobs`：生成任务。
- `script_candidates`：脚本候选。
- `script_reviews`：人工审核与复盘。

当前已有表可以迁移或映射，不必一次推翻。

## 7. 大版本开发路线

### V2.0：信息架构重构

目标：把单页 MVP 变成真正的内容工作台。

交付：

- 左侧菜单改成 6 个页面。
- 今日工作台清空旧历史默认展示。
- 历史脚本移入脚本库页。
- 生成流程页只显示当前工作流。
- 数据状态卡展示采集、字幕、生成状态。

验收：

- 页面刷新后不再把历史脚本当成当前结果。
- 运营能清楚知道今天从哪里开始。

### V2.1：人工导入和对标内容池

目标：解决自动采集不稳定时的可用性。

交付：

- 对标内容池页面。
- 视频链接导入。
- 批量链接导入。
- 手工字幕粘贴。
- 对标账号池维护。
- 第三方表格粘贴导入。
- 导入后批量加入生成工作流。
- 导入后批量生成结构摘要。

验收：

- 不依赖抖音搜索，也能导入 10 条对标视频并进入结构摘要。
- 自动采集失败时，运营能从采集任务中心跳到对标内容池，用人工或第三方数据继续完成当天生产。

### V2.2：字幕结构化闭环

目标：把字幕项目真正接入系统。

交付：

- 调用 `video-tools /api/subtitle`。
- 字幕任务状态。
- 字幕文本入库。
- Codex CLI 结构摘要。
- 页面展示可用结构。

当前原型已落地：

- 对标内容池单条素材可手工补录/更新字幕文本。
- 手工补录后素材状态变为 `subtitle_done`，结构摘要会读取该文本。
- 这条链路作为 `video-tools` 自动字幕服务前的替代方案，保证没有自动字幕时也能完成结构化和脚本生成。

验收：

- 一条视频链接可以变成字幕文本和结构摘要。
- 结构摘要可以被脚本生成读取。

### V2.3：脚本质量引擎

目标：让脚本从“能生成”变成“可拍可用”。

交付：

- 新提示词模板。
- 商品活动输入。
- 质量评分。
- 低分自动重写。
- 脚本卡展示评分和可拍理由。

验收：

- 每条脚本包含具体镜头、场景、道具、口播、字幕、CTA。
- 低质量脚本会被标记或自动重写。

### V2.4：采集任务中心

目标：把采集变成可监控任务，而不是命令行脚本。

交付：

- 抖音热榜任务。
- 小红书/第三方热点任务占位。
- 登录态健康检查。
- 采集失败截图和错误记录。
- 手动重跑按钮。

验收：

- 运营能看到今天采集是否成功。
- 登录态失效时明确提示，不误用旧数据。

### V2.5：复盘与学习闭环

目标：用真实发布表现反向优化生成。

交付：

- 标记脚本采用状态。
- 回填发布链接。
- 回填表现数据。
- 标记优质脚本模板。
- 生成时引用历史优质模板。

验收：

- 系统能区分“生成过”和“真正被采用且表现好”的脚本。

## 8. 第一阶段优先级

下一轮开发不要同时做所有事。建议按这个顺序：

1. V2.0 信息架构重构。
2. V2.1 人工导入和对标内容池。
3. V2.2 字幕结构化闭环。
4. V2.3 脚本质量引擎。

原因：

- 先把产品形态改对，否则继续堆功能会越来越乱。
- 人工导入是采集不稳定时的生命线。
- 字幕结构是脚本质量提升的关键输入。
- 质量引擎必须建立在更厚的输入之上。

## 8.1 V2.0 状态模型

V2.0 最先要解决的不是更多生成能力，而是“页面状态混在一起”的问题。

当前 MVP 最大的体验问题：

- 页面刷新后会看到历史脚本，用户误以为这是当前生成结果。
- 选题分析、脚本列表、历史脚本库没有明确边界。
- 数据源状态只是隐含在页面内容里，没有作为系统状态展示。

V2.0 必须明确四类状态。

### 1. 今日工作流状态

这是运营当天正在操作的内容。

包含：

- 今日已选热点。
- 今日已选对标内容。
- 当前确认包。
- 当前生成任务。
- 当前生成结果。

规则：

- 页面刷新默认从空工作流开始。
- 历史结果不自动进入今日工作流。
- 今日工作流只展示当前批次结果。

### 2. 历史资产状态

这是已经入库的长期资产。

包含：

- 历史脚本。
- 历史结构摘要。
- 历史字幕。
- 历史采用和复盘。

规则：

- 只在脚本库、对标内容池或复盘页展示。
- 不默认污染今日工作台。
- 可以被用户主动引用为生成参考。

### 3. 数据源状态

这是系统输入是否可靠的状态。

包含：

- 热榜最近采集时间。
- 登录态是否有效。
- 类目采集是否失败。
- 字幕服务是否可用。
- 人工导入是否有待处理素材。

规则：

- 首页必须可见。
- 失败要显示原因。
- 旧数据要标记时间，不能假装是今天数据。

### 4. 生成任务状态

这是一次生成动作的生命周期。

状态：

- 待选择素材。
- 待确认输入。
- 待结构分析。
- 生成中。
- 已生成。
- 低质量待改写。
- 已入库。
- 失败。

规则：

- 脚本列表只展示“已生成”的当前任务结果。
- 失败和低质量不能静默兜底。
- 兜底生成必须明确标记来源和原因。

## 9. 明确不做

V2 首阶段不做：

- 全自动发布。
- 全平台自动爬取。
- 多租户权限。
- 公网部署。
- 复杂 BI 看板。
- 官方 API 深度集成。

这些会增加复杂度，但不能解决当前最核心的脚本质量和每日工作流问题。

## 10. 成功标准

V2 阶段成功不是页面更好看，而是满足下面指标：

- 运营每天能从“今日工作台”开始，而不是从历史结果里找入口。
- 没有自动采集时，仍能靠人工导入完成内容生产。
- 固定对标账号池不只停留在账号名单；首页必须能指定一个账号，展示“补近期内容 -> 补字幕/正文 -> 加入生成 -> 结构摘要 -> 生成脚本”的首条真实账号素材跑通计划。
- 至少 10 条对标视频能完成字幕和结构摘要。
- 每天能生成 5-10 条带来源依据、可拍分镜和风险提示的脚本。
- 每条脚本能标记是否采用。
- 已采用脚本能回填表现，形成下一轮优化输入。

## 11. 首条真实账号素材跑通计划

当前大版本推进的第一优先级不是继续增加页面，而是证明固定对标账号能贡献真实输入。

V2 首页新增 `firstBenchmarkMaterialPlan`，从今日固定对标账号更新任务中选择一个最需要处理的账号，生成可执行计划：

- 目标账号：账号名、平台、类目、为什么追踪。
- 当前计数：已导入、有字幕/正文、已加入生成、已结构化、可生成。
- 五步状态：补 1 条近期内容、补字幕/正文、加入生成工作流、生成结构摘要、生成候选脚本。
- 跑通证据：真实作品链接或可追溯来源、30 字以上字幕/正文/结构观察、结构摘要、候选脚本输入证据。
- 替代路径：真实链接优先、手工字幕兜底、第三方表格兜底。
- 排除规则：示例、测试、验证、空链接、只有账号名或只有热词都不计入跑通。

验收口径：

- 页面不能为了显示跑通而创建模拟素材。
- 如果当前没有真实账号素材，必须显示缺口和导入入口。
- 如果已有素材但缺字幕、缺选择或缺结构，必须显示卡在哪一步。
- 只有至少 1 条账号素材同时具备文本、已加入生成、结构摘要，才允许显示“可生成”。
- 内容池里的 P0-1 任务单只能提供空白字段和验收说明，不能预置示例链接；空白行必须被预检阻塞，避免运营把模板误当真实数据导入。

## 12. 下一大版本实施计划

V2 首页的开发看板新增 `implementationPlan`，把路线图拆成可执行任务包。

V2 首页同时新增“下一大版本作战区”，读取 `GET /api/v2/dashboard.v2MasterPlan`。它不是新的静态规划页，而是把现有真实状态聚合成一个开发入口：

- 最终目标：说明系统不是脚本生成页，而是每日内容生产闭环。
- 当前现实：明确当前仍只是 MVP 小版本，不能把原型验收当目标系统完成。
- 当前卡点：直接读取当前优先任务包，例如 P0-1 首条真实账号素材闭环。
- 大版本开发包：聚合 P0-1、P0-2、P1-1、P1-2 的范围、验收、证据和入口。
- 目标体验：把运营一天的使用路径聚合到同一个区块。
- 采集替代方案：把公开热榜、登录态小批量、人工导入、第三方表格四层保障集中展示。
- 验收红线：没有真实素材、没有兜底链路、没有输入依据和审核状态时，不允许宣称大版本完成。

V2 首页还新增“V2 大版本验收总表”，读取 `GET /api/v2/dashboard.v2AcceptanceBoard`。它的作用是把作战区从“规划入口”推进到“发布门槛”：

- 总状态：显示 R1-R4 整体满足多少项、仍有几个版本阻塞。
- 分版本验收：每个版本展示已满足项、缺口项、当前证据和下一动作。
- 优先入口：自动指向当前最该处理的版本缺口。
- 验收红线：继续沿用大版本实施计划的 gates。
- 成熟度提醒：即使 R1-R4 全绿，也继续提示自动字幕、对标账号更新、质量学习和第三方清洗等目标系统缺口。

V2 首页进一步新增“下一步执行队列”，读取 `GET /api/v2/dashboard.v2ExecutionQueue`。它解决的问题是：验收总表可能显示 R1 的表层缺口是“生成脚本”，但真实依赖其实是 R2/P0-1 的“先补真实输入”。执行队列必须按依赖排序：

1. 先补首条真实账号素材。
2. 再补齐生成准备度。
3. 再生成候选脚本并进入审核队列。
4. 自动采集失败时切人工或第三方兜底，不继续硬跑登录态采集。

执行队列每一项都要显示：

- 为什么现在先做这一步。
- 当前证据是什么。
- 谁负责。
- 点击后去哪里处理。
- 完成后会解锁哪些 R1-R4 验收项。

任务包顺序：

1. P0-1 首条真实账号素材闭环：先跑通 1 个固定对标账号的 1 条真实近期内容。
2. P0-2 输入增厚与生成准备度：让热点、结构素材、商品活动和模板都进入生成输入包。
3. P1-1 脚本质量与复盘学习：补质量诊断、审核原因、发布表现和模板沉淀。
4. P1-2 采集保障和替代数据链路：把公开热榜、登录态小批量、人工导入、第三方表格做成可切换链路。

红线：

- 没有真实素材证据，不允许把输入增厚标成完成。
- 自动采集失败必须有人工或第三方兜底入口。
- 生成脚本必须能回看输入依据、质量诊断和审核状态。
- 原型验收通过不等于目标系统完成，仍需看下一档成熟度缺口。
